# Chrome、Edge、Firefox 的书签终于能共用一份了，数据还躺在自己网盘里

**导读：** 这篇讲一个开源浏览器扩展 Konode。它不注册账号、不要谷歌账号，把书签、标签页、历史记录同步到你自己的网盘或 GitHub 上，还能让 Chrome 和 Firefox 互相同步。我把官方仓库从头翻了一遍，顺手揪出某篇介绍文章里一个挺明显的硬伤。



## 用多个浏览器的烦恼

我日常要开三个浏览器。

公司那台 Windows 自带 Edge，上面存了一堆运维后台和云厂商控制台；家里笔记本常用 Chrome，收藏夹里全是文档和教程；偶尔调前端会开 Firefox，又攒了第三套。

同一个页面，我收藏了三遍。

更烦的是历史记录。上周在公司查到的那个解决方法，回家想找回来——Edge 的历史躺在公司电脑上，Chrome 这边一条都没有。

用官方同步？谷歌账号要先解决能不能连上的问题，Edge 和 Firefox 各有各的账号体系，三家互不相认。

所以刷到 Konode 的时候我是有点意外的：这东西居然国内能直接用，而且真的把这件事做成了。



## Konode是什么

一句话：**一个浏览器扩展，把你的浏览器数据写进你自己指定的存储里，中间没有任何厂商服务器。**

拆成三个关键点：

- **不用注册。** 没有「Konode 账号」这个概念，装好扩展直接配存储就能用。
- **数据不在别人手里。** 它不提供云存储、不收集遥测。你的书签从浏览器直接进你的 Google Drive、GitHub 私有仓库，或者你自己的 WebDAV。
- **真的跨内核。** Chromium 全家（Chrome、Edge、Brave、Helium、ungoogled-chromium）和 Firefox 系（含 Waterfox）共用同一套同步文件。**Chrome 的书签能同步到 Firefox，这件事三家官方同步都做不到。**

开源，MPL-2.0 协议，TypeScript 写的，仓库在 GitHub 上叫 `konabe-studio/konode`。2026 年 5 月建仓，到现在三百多个 star。

说实话 star 不多，我不打算吹它火。但这恰恰说明作者没在营销上花力气——到底能不能用，得自己装上试。

顺便一个细节：README 里作者自己写了「构建过程有 AI 参与（Claude Code），人工 review 后维护」。这种话愿意明着写出来，我反而觉得靠谱。

## 可以同步什么

它能同步的比你想象的多一点：

- **书签。** 完整保留文件夹层级和嵌套，重命名、移动、文件夹重排都会跟着走，删除也会同步——不会出现「删了半天过几天自己长回来」
- **打开的标签页。** 以会话快照的形式存，换台设备能一键把整个浏览现场接回来
- **历史记录。** 合并去重成一份清单，任何设备上都能搜到全部记录
- **扩展列表。** 只同步清单，告诉你新机器上缺了哪几个扩展。**它不会替你装、也不会替你卸**，权限是只读的

密码、Cookie、自动填充这些，它一个都不碰。

原因和「安全问题」不太一样，我觉得理由更硬：**浏览器扩展根本读不到浏览器原生的密码库。** 这是浏览器自己划的安全边界，不是 Konode 偷懒。

所以密码这事老老实实交给 Bitwarden、1Password 这类专业工具，别指望浏览器同步扩展顺手解决。

## 数据放哪儿

它支持三类存储：

| 后端         | 怎么用                                                       | 适合谁                         |
| ------------ | ------------------------------------------------------------ | ------------------------------ |
| Google Drive | 一次登录，只申请 `drive.file` 窄权限，只能碰它自己创建的文件 | 海外用户，最省事               |
| GitHub       | 指向一个**私有**仓库，每次同步落一个 commit                  | 开发者，白捡版本历史           |
| WebDAV       | 地址 + 账号 + 应用专用密码                                   | 有 NAS、有 VPS、或用坚果云的人 |

Google Drive 在国内基本用不了，这一栏可以直接跳过。剩下两个都挺香：

**GitHub 后端有个隐藏彩蛋。** 每次同步就是一次 commit，你的书签从此有了版本管理——能 diff、能回滚、能看「上周到底删了哪一堆」。这个设计对开发者来说很戳。

**WebDAV 后端最接地气。** 坚果云、群晖、Nextcloud、pCloud、Koofr、Fastmail 都有预设地址，填三个空就行。国内最省事的其实是坚果云，免费额度用来放书签完全够。

还有一类玩法是**自己建 WebDAV**。手上有 VPS 或 NAS 的，跑个 WebDAV 服务，数据就躺在自己硬盘上，谁也碰不到。

自建 WebDAV 对机器要求极低，1 核 1G 都能跑：装个 nginx 加 dav 模块，或者 `rclone serve webdav` 一条命令就起来了。我自己是习惯把这类小服务扔云上，图个省心——不用管电、不怕硬盘坏、出问题换一台接着跑。

机器我平时走官方渠道买，顺手放两个入口：**阿里云 y.xgss.net/a** / **腾讯云 y.xgss.net/tx**。新用户那块活动机，跑个 WebDAV 绰绰有余，一年也就一顿饭钱。

**但有个前提别踩：WebDAV 强制 https，明文 http 会被直接拒掉**（只有 localhost 例外）。所以自建的话，域名和证书得先配好，别拿 IP 裸奔。



## 加密：开着安心，钥匙丢了就真没了

加密是**可选的**，在设置向导里决定，你没选之前它一个字节都不上传。

打开之后是 AES-256-GCM 端到端加密，密钥用 PBKDF2-SHA256 从口令派生，迭代 60 万轮。存进网盘的 JSON 打开全是密文，就算你哪天不小心把 GitHub 仓库设成公开，别人拿到的也只是一堆乱码。

代价很实在：**口令丢了，数据永久解不回来。** 官方连「口令至少 12 位、每台设备必须完全一致」都写进文档了，不一致的时候它会直接报错，而不是悄悄把你数据分成两份读不了的密文。

我的建议是：要么用生成的长密钥、存进密码管理器；要么就别开——开了又不好好存钥匙，等于给自己埋雷。



## 真会踩的坑

- **WebDAV 密码别用主账号密码。** 坚果云这类要去设置里生成「应用专用密码」。粘贴的时候多一个空格就会一直报错，而且报错信息看不出来是空格——我见过有人为这个查半晚上。
- **GitHub 后端必须是私有仓库。** 公开仓库会被直接拒绝。token 用 fine-grained，只给那一个仓库的 Contents 读写权限，记得设个你记得住的过期时间——token 到期同步会静默停掉。
- **换后端不迁移数据。** 官网原话是「当成重新开始」。写进网盘里的文件还在，但两边不会互相搬。
- **第一次同步先把书签导出备份。** 尤其是第一次开历史记录，那是一次大量写入，配置错了轻则失败，重则把云端旧数据搞乱。
- **手机端只有 Firefox for Android 能凑合用，而且只能同步标签页。** 安卓版 Firefox 跑扩展的环境（GeckoView）没有书签和历史 API，扩展压根读不到。这跟开发者水平无关，是平台限制。
- **历史记录的时间会「失真」。** Chromium 系恢复过来的条目显示的是同步时刻，不是当初的访问时间，因为浏览器不给扩展写访问时间的权限；Firefox 能保留原始时间。访问次数两边都恢复不了。



## 谁适合用

**适合：**

- 电脑上同时装了两种以上浏览器，书签已经分裂的
- 有 NAS 或 VPS，本来就想把数据放自己硬盘上的
- 用 Brave、Helium 这类 Chromium 套壳浏览器，官方同步不给力的

**别折腾：**

- 只用过一个浏览器、官方同步够用的——没必要给自己找事
- 已经在用 Floccus 同步书签、且满意的。它做书签这件事很成熟，别为了折腾而折腾
- 主力是 Safari 的。官方支持列表里没有 Safari，扩展那套 API 苹果走的是另一条路
- 想同步密码的。前面说了，扩展读不到密码库，这不是软件问题



## 最后

装完之后我最大的变化是：家里笔记本打开 Chrome，公司 Edge 上存的那批运维后台链接直接就在收藏栏里，不用再翻聊天记录找地址。

它没有多神奇。就是把「三个浏览器三套书签」这个别扭，变成了「一份书签三个入口」。

如果你也跟我一样，浏览器装了一堆、书签散得到处都是，这东西值得花十分钟配一下。

你电脑上现在装了几个浏览器？书签是怎么处理的——官方同步、还是干脆不存？评论区聊聊。
