# 免费

## 一、先把钱算清楚：到底省的是什么

我不喜欢「零成本」这种说法，因为它总会漏掉一个前提。这里的前提很明确——**域名本身要钱**。

`.com` 一年几十块，`.xyz` 之类的首年更便宜。这是唯一一笔绕不过去的硬支出。除此之外：

| 项目                   | 实际花费                       |
| ---------------------- | ------------------------------ |
| 服务器 / VPS           | **0**，根本没买                |
| 邮箱系统本身           | **0**，MIT 开源                |
| 数据库、缓存、文件存储 | **0**，吃 Cloudflare 免费额度  |
| 发信通道               | **0**，Resend 免费档 100 封/天 |
| 附件存储               | **0**，R2 免费 10 GB           |
| 域名                   | 几十块一年                     |

所以准确的说法不是「零成本」，是**「除域名外零成本」**。

省下来的其实是两块：一是那台你本来要买的服务器，二是企业邮箱按人头收的那笔年费。

对个人和小团队来说，第二块才是大头。

## 三、它到底能干什么

官方的功能列表挺长，我挑真正影响使用的说：

- **收信 + 发信**：发信走 Resend，支持群发、内嵌图片、带附件，发出去还能查状态
- **附件**：存 Cloudflare R2，收发都行
- **多号模式**：一个账号下挂多个邮箱地址，像正规邮箱平台那样切换
- **验证码识别**：用 Workers AI 直接读邮件里的验证码，不用点进去看
- **邮件推送**：收到信自动转给 TG 机器人，或者转到你常用的邮箱
- **开放 API**：批量建账号、按条件查邮件
- **后台管理**：RBAC 权限、限制某个用户能用多少资源
- **数据看板**：ECharts 画邮件增长曲线
- **人机验证**：接的 Turnstile，防批量注册

对我来说，真正值钱的是**验证码识别**和**多号模式**。

前者是给自动化流程用的——注册、登录、找回密码，这些场景都要读验证码，以前得写一堆正则去抠，现在交给模型认，稳得多。

后者是给「一个人要管好几个身份」用的。做测试、跑爬虫、给不同业务分邮箱，一个面板全切完，不用来回登。

## 四、三件事必须先想清楚

这三条我翻文档翻了半天才理清楚，也恰恰是新手最容易卡住的地方。放在动手之前说。

### **第一，域名必须托管到 Cloudflare。**

不是在 Cloudflare 加个域名记录就行，是要把域名的 NS（域名服务器）整个改成 Cloudflare 给的那两个。这一步不改，后面什么都做不了。

代价是：这个域名原来的解析记录会一起搬过去，得提前导出来，别改完发现网站打不开了。

### **第二，收信不是 Workers 自己收的。**

它靠的是 Cloudflare 免费的 **Email Routing**——这个功能专门负责接住发到你域名的邮件，然后再投递给 Worker 去处理。

所以流程是这样的：别人发到 `hi@你的域名`，Cloudflare 接住，Worker 解析，存进 D1，附件丢进 R2。

Email Routing 本身不额外收费，配好就行。

### **第三，发信要靠 Resend，而且得验证域名。**

Resend 不是填个 API Key 就能用。你得在它后台添加自己的域名，然后按它给的提示去 DNS 里加几条记录（SPF、DKIM 那一套），验证通过才能发。

这一步不做，代码跑起来也会一直报发信失败。

**另外还有个小坑**：默认给的 `xxx.workers.dev` 域名，国内访问经常不稳。正经用一定要绑自己的域名，别拿默认域名测完就以为成了。

## 免费额度到底够不够用

这是我最关心的部分，因为「免费」两个字最怕的是用到一半突然收费。

我把官方价格页翻了一遍，2026 年 10 月的口径是这样：

| 资源         | 免费额度                               |
| ------------ | -------------------------------------- |
| Workers 请求 | 10 万次/天                             |
| D1 数据库    | 500 万行读/天，10 万行写/天，5 GB 存储 |
| KV 缓存      | 10 万次读/天，1000 次写/天，1 GB       |
| R2 附件存储  | 10 GB/月，出站流量免费不限             |
| Workers AI   | 1 万 Neurons/天                        |
| Resend 发信  | 100 封/天，3000 封/月                  |

拿这个额度对一下实际使用：

**收信**，一天几百封都算多的，10 万次请求够你用很久。

**发信**，100 封/天是真正的天花板。自己用、小团队内部用完全够；要是拿它跑营销邮件，第二天就撞墙了。

**附件**，10 GB 是唯一我觉得可能顶到的地方。别人发来的大附件会一直躺在 R2 里，不清就一直占着。

**验证码识别**，1 万 Neurons 一天，具体消耗跟模型有关，按常见的识别量估算，一天认几百封问题不大。

结论：**个人用绰绰有余，十几人的小团队也够，唯一要盯的是 R2 存储和每天的 100 封发信上限。**



## 几个我必须提前说的坑

有几个地方是真的会让人翻车，不说清楚不厚道。

**别动已经在用的邮箱。**

如果这个域名上已经有企业邮箱在跑，千万别为了玩这个去改 MX 记录。改完的结果就是老邮箱全线收不到信，而且恢复起来很麻烦。

想试，拿一个子域名（比如 `mail.你的域名`）单独试。

**新域名发信，大概率进垃圾箱。**

域名越新，发信 reputation 越差。发给 QQ、163 这些大厂邮箱，头几封很容易被判成垃圾邮件，甚至直接退信。

这不是项目的问题，是邮件这套老规矩决定的。慢慢养，别一上来就群发。

**重要验证码别绑在这上面。**

银行、支付、政务这类验证码，一旦漏收就是大事。自建邮箱出问题的概率不高，但也不是零——Cloudflare 抖一下、额度超了、代码更了一版，都可能让你收不到那封关键邮件。

我的建议：**重要账号继续用大厂邮箱，自建这套拿来接不重要的、量大的、需要自动化的。**

**数据在你手上，备份也得你自己做。**

这是自建的好处，也是代价。邮件都存在 D1 里，附件在 R2 里，哪天你想迁移，得自己去导出。

建议养成习惯：定期把 D1 导一份出来，丢到别的地方存着。

**一键部署 = fork 一个仓库。**

官方的部署按钮背后就是帮你 fork 一份到自己的 GitHub。这没问题，但要注意**别把 API Key、Resend 的密钥写进公开仓库的代码里**，那些应该放在 Cloudflare 的环境变量里。



## cloud]‑mail适合谁

我列一下，对号入座就行。

**适合：**

- 手里有域名，想搞个 `@自己域名` 的邮箱，又不想按人头付费的个人
- 十几人的小团队，需要几个分部门的邮箱地址
- 要跑自动化的人，需要能读验证码、能批量建号的邮箱
- 做测试的，需要临时邮箱收注册确认信

**不太适合：**

- 完全没域名、也不想买域名的（第一步就得掏钱，别被「免费」两个字骗了）
- 要收重要验证码的（还是大厂邮箱稳）
- 想拿它做营销群发的（100 封/天的上限，不够看）
- 完全不懂 DNS 的（改 NS、加 SPF/DKIM，这几步绕不过去）



## 我的建议

别一上来就把主域名的邮箱全搬过来。

**先拿一个子域名试水**，跑通收信、发信、附件、验证码这一整条链路，用一两周，觉得稳了再考虑扩大。

这中间你会遇到几个具体问题：DNS 记录加错、邮件进垃圾箱、附件传不上去。在一个不重要的子域名上踩这些坑，代价最小。

至于「值不值得折腾」，我的判断是这样：

如果你只是想要个 `@自己域名` 的邮箱，按官方的路子走，一小时之内能跑起来，之后基本不用管。这种情况下，**折腾的成本远低于一年几千块的企业邮箱**。

但如果你要的是一个「什么都能干、绝对不能出问题」的邮箱，那还是老实买企业邮箱。免费的东西，代价通常是你得自己当运维。
