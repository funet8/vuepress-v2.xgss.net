## 一、WorkBuddy免费服务器的原理

你在沙箱里起一个监听本地端口的服务（比如 :3000），背后平台其实帮你干了三件事：

1. **给你发个公网域名**：形如 `<沙箱ID>.app.workbuddy.host` 的 HTTPS 子域名，自动分配，不用申请。
2. **腾讯云 CLB 帮你把 HTTPS 证书的事儿扛了**：TLS 在负载均衡那一层就终止掉，你完全不用碰证书。
3. **沙箱里有个 sandbox-proxy 在做反代**：流量进沙箱后，它负责把请求转给你本地那个端口。

一句话总结：**你在本地 :3000 起服务，公网 `https://<沙箱ID>.app.workbuddy.host` 直接就能访问到。**

 反向代理、证书、nginx——全都不用你管。

对只想"把东西跑起来让别人看见"的人来说，这套省掉的可不是一步两步，是一整套运维的烦心事。

## 二、三步跑起来！简单

**第 1 步：在沙箱里起一个本地服务**

随便什么能监听端口的服务都行——Node、Python、Java 后端，甚至一个静态文件服务器。在沙箱终端里把它跑起来，让它监听某个本地端口（比如 :3000）。此时服务还只在沙箱内部，外网访问不到，这是正常的。

**第 2 步：找到你的公网域名**

平台会给当前沙箱分配 `<沙箱ID>.app.workbuddy.host`。这个域名一般在沙箱信息或任务面板里就能看到，或者按规则拼出来（沙箱ID 就是平台给你的那个标识）。

**第 3 步：直接公网访问**

不用配任何东西。把上一步拿到的域名前面加上 `https://`，直接粘进浏览器打开。

CLB 已经在云端把 HTTPS 卸完了，sandbox-proxy 也把请求送到了你本地 :3000。页面能正常打开，链路就通了。

想把服务换成你自己的？直接把演示服务换成你的真实后端就行。只要它监听本地某个端口，域名就自动指向它。换端口的话，确认 proxy 转发规则覆盖到那个端口即可。

## 四、能干什么

下面这些场景，传统做法你至少得买台轻量云服务器、配 nginx、申请证书。在沙箱里，几分钟搞定。

| 场景                    | 以前怎么搞                 | 现在怎么搞                         |
| ----------------------- | -------------------------- | ---------------------------------- |
| 临时演示 / Demo         | 部署到云服务器或 Vercel    | 本地起服务，甩个 https 链接给客户  |
| Webhook 接收端          | 得有台公网可达的固定服务器 | 沙箱域名直接填进 GitHub / 支付回调 |
| 小程序 / 公众号后端联调 | 必须 HTTPS 公网域名        | 自带 HTTPS，证书麻烦省了           |
| 第三方 OAuth 回调地址   | 需要可信 HTTPS 域名        | 子域名天生 HTTPS，直接填           |
| 内网穿透替代            | 装 frp / ngrok             | 沙箱本身就是公网出口               |
| 快速托管静态页          | 对象存储 + CDN             | 起个静态服务器就行                 |

几个我实际觉得好用的：

- **给自己的 agent 当"手脚"**：如果你在搭智能体，需要它对外提供一个能被调用的 HTTP 接口（收外部事件、接回调结果），把接口跑在沙箱里，立刻就有个公网 HTTPS 端点，不用额外搞基础设施。
- **给同事临时开个服务**：做好的原型想让人看？不用让他装环境，发个链接就行。会话在，服务就在；沙箱回收，链接自然失效。这种"阅后即焚"的属性，反而适合放一些不该长期暴露的演示。
- **验证 TLS 相关逻辑**：CLB 帮你做了 TLS 终止，你可以拿它快速测"我的服务在真实 HTTPS 环境下到底正不正常"。



## 五、怎么保活

前面说了，沙箱是按会话存在的，会话一断服务就没。但如果你真想让它多撑一会儿——比如挂个长期联调的接口、或者演示要放好几天——有几招能延长它的寿命。

### 1. 别让会话空转断掉

沙箱大多有空闲超时，长时间没有任何活动就可能被回收。最简单的保活就是让它"看起来一直在忙"：起一个会定时打日志的常驻进程，或者在终端里挂一个周期性心跳（比如每分钟 echo 一下、或者跑个 `while sleep 60; do date; done`）。有持续输出，会话一般就不会被判定为闲置。

### 2.把服务以后台进程方式跑

别在前台直接 `node server.js` 然后关终端——终端一关进程就跟着没了。用 nohup 或 `&` 把它丢到后台，再 disown 一下，让服务和终端解绑：

```bash
nohup node server.js > app.log 2>&1 &
```

这样即使你退出了对话界面，只要沙箱没被回收，服务还在跑。

### 3.让 WorkBuddy 自己盯着它

这招最省心。你可以直接给它下指令，让它帮你保活：

> 请帮我把这个服务以后台进程方式常驻运行，并每隔一会儿输出一次心跳日志，确保沙箱不因空闲被回收。如果服务意外退出，请自动重启它。同时告诉我当前公网域名是否还能正常访问。

它自己会去挂进程、加心跳、顺手帮你看域名还通不通。

### 4.实在要长期，还是得上正经托管

保活只是"拖时间"，不是"买保险"。沙箱本质是云端任务环境，平台随时可能按策略回收。如果你这个服务要 7×24 稳定运行，别跟沙箱较劲——老老实实搞台轻量云服务器或上容器平台，那才是正路。



## 六、避坑

不要放重要的信息！不要放重要的信息！不要放重要的信息！

- **沙箱活着，服务才活着**。沙箱是按会话/时段存在的，会话结束或回收，域名和服务一起没。它适合临时、演示、联调，别拿当生产环境长期托管。
- **别往里塞机密或长期数据**。它是云端任务环境，不是你的私有服务器，凭据、数据库别长期搁里面。
- **端口和转发规则以平台实际为准**。具体支持哪些端口、有没有限流，以 WorkBuddy 官方说明为准。
- **域名是平台分配的**，你不能自定义成自己的品牌域名（除非平台另有自定义域名功能）。要对外长期用，还是得走正经托管。
