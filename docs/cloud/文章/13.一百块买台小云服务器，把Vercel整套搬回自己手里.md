# 如何使用海外节点云服务器，把Vercel整套搬回自己手里



**导读：** Vercel 好用，但国内打开慢、额度紧、想跑个带数据库的全栈项目处处受限。这篇讲我现在的做法——海外节点的云服务器 + 开源自建平台 Dokploy，再把它接给 AI，一句话就把项目部署上线。照着做大概一个下午能跑通。



## Vercel的不足

Vercel 是我入门时最顺手的工具，推一下代码就上线，域名 HTTPS 全都自动配好，那种感觉确实爽。

但用久了会碰到两堵墙。

**第一堵是网络。** 国内直接访问经常抽风，有时候干脆打不开。你辛辛苦苦做完的东西发给朋友试用，对方第一句是"我这边加载不出来，是不是要挂梯子"——这个体验，做产品的人应该都懂有多劝退。

**第二堵是边界。** 免费额度抠得很紧，Serverless 函数冷启动慢，想跑一个常驻后台任务、想配一个自己能连的自建数据库，就开始四处碰壁。它适合"网页放上去看看效果"，不太适合"我要长期养一个东西"。

所以我现在的做法变成了：**自己买一台小服务器，在上面装一个自建部署平台。**

![img](https://imgoss.xgss.net/picgo-tx2026/QQ_1793186333435.png?tx)

## Dokploy 是什么

Dokploy 是一个开源的部署平台，官方自己的定位写得很直白：**Vercel、Netlify、Heroku 的开源替代品**。

GitHub 上 3.8 万多个 Star，主仓库 TypeScript 写的，2024 年才建的项目，到现在几乎每天都在更新——我写这篇的时候最新版本是 v0.30.10，再往前一个版本是三天前发的。这种更新频率，说明它是活的，不是那种建完就放着吃灰的开源项目。

它跟宝塔最大的区别在于底层：**全部跑在 Docker 容器里**，每个应用互相隔离。你这台机器上放了五个项目，其中一个把内存吃爆了，另外四个也不会跟着遭殃。宝塔时代那种"一个 PHP 版本搞坏整台机器"的噩梦，在这套体系里基本不会发生。

顺便说个我特别喜欢的地方：它底层自带了 Traefik 反向代理。域名解析过来，面板里填一下，**HTTPS 证书它自己去 Let's Encrypt 申请自动续期**，不花钱也不用管。



## VPS、Dokploy、MCP

别看教程一堆术语，真正要理解的只有三个东西：

**VPS** —— 就是你租的云服务器。理解成一台 24 小时开机、连着网的电脑，专门用来跑你的项目和数据库。

**Dokploy** —— 管理这台电脑的操作台。你不用记 Linux 命令，所有操作在网页面板上点点就行。

**MCP** —— AI 操作 Dokploy 的接口协议。接上之后，你可以直接跟 AI 说"把这个项目部署上去"，它自己去建项目、拉代码、看日志。

整个流程就一句话：

> **你在对话里吩咐一句 → AI 通过 MCP 调 Dokploy → 你自己的服务器把网站跑起来**

说实话，我第一次跑通这个链路的时候有点愣住。以前部署是要背命令、看文档、踩坑的活儿，现在变成一个对话任务了。





## 买云服务器

### 1.节点千万别选大陆

这是本文最重要的一条建议，比选配置重要得多。

服务器如果在**大陆节点**，你想绑自己的域名，就必须走工信部 ICP 备案——填资料、拍身份证、等审核，快则几天慢则半个月。对一个个人折腾的小项目来说，这套流程足够让你放弃。

选**香港、新加坡、东京**这些海外或港澳台节点，域名解析过去马上生效，零备案，五分钟能用上自己的域名。

### 2.别一上来就追大配置

2 核 2G 跑普通小项目完全够。但要注意，Docker 容器开多了——尤其后面如果要部署 Supabase 这种"全家桶"——启动那一下内存会有小高峰，容易触发 OOM 把进程杀掉。

实测阿里云的2核2G的配置，已经是不堪重负。

**经过实测最低的配置需要4核8G的配置！**

## 安装dokploy

### 1.装面板

登录服务器终端（网页版的免密连接就够用，不用配密钥），用管理员权限跑官方安装脚本：

```bash
sudo su -c 'curl -sSL https://dokploy.com/install.sh | sh'
```

装完会提示已完成。如果镜像本身预装了 Docker，过程中会显示 `Docker already installed`，正常。

![img](https://imgoss.xgss.net/picgo-tx2026/QQ_1793094454787.png?tx)

**装之前先确认一件事**：80、443、3000 这三个端口没被别的服务占着。

如果这台机器上已经跑了别的网站，先看一眼现有服务再动手，不然会打架。

接下来去云厂商控制台的**防火墙**页面，放行 TCP 3000。这一步很多人会漏，漏了就会一直打不开面板，然后误以为是安装失败。

![img](https://imgoss.xgss.net/picgo-tx2026/QQ_1793094731852.png?tx)

浏览器打开：

```
http://你的服务器公网IP:3000
```

![img](https://imgoss.xgss.net/picgo-tx2026/QQ_1793094763836.png?tx)

出来初始化页面，填名字、邮箱、密码，点 Register 建管理员账号。

这个账号是你这台 Dokploy 自己的，跟云厂商账号没有关系，随便设。

首次登录会弹使用引导，点左下角 **SKIP ALL** 直接进控制台。别急着研究每个菜单，先让 AI 连上，回头再看它建了什么。



### 2.生成 API Key，把面板交给 AI

打开左侧 **Profile**，往下滚找到 **API / CLI Keys**，点右下角 **Generate New Key** 生成。

生成的那串密钥**复制下来存好**，后面要填到配置文件里。这把 Key 就是 AI 访问你部署面板的凭证——所以理解成密码，别乱发。

接下来在 AI 编程工具里新建一个任务，第一句话先让它装 MCP。

![img](https://imgoss.xgss.net/picgo-tx2026/QQ_1793094907170.png?tx)

星哥以 workbuddy（当然也可以用其他的ai agent） 为例，把地址换成你自己的：

```
请帮我安装并配置 Dokploy 官方 MCP，供 Codex 使用。

Dokploy 地址：http://你的服务器公网IP:3000

保留现有配置，API Key 先留占位符，告诉我在哪里填写。

完成后展示配置结果，方便我截图。

暂时不要部署项目。

```

![img](https://imgoss.xgss.net/picgo-tx2026/QQ_1793095145198.png?tx)

官方 MCP 的 npm 包名是 `@dokploy/mcp`，版本也一路跟着主仓库走，我查的时候是 0.30.7。

执行完毕

```
已安装 Dokploy 官方 MCP：@dokploy/mcp@0.30.7
已配置给 Codex CLI 使用
已保留原有 Codex 配置
已创建原配置备份
API Key 已使用占位符
Codex 检测状态：enabled
未连接 Dokploy 实例
未执行任何项目部署或资源变更
```



**这里有个小建议：** 密钥别直接甩进聊天框。让它先写个占位符，然后你按它回复的路径，自己打开配置文件（比如 Codex 的 `config.toml`），找到这一行：

```toml
DOKPLOY_API_KEY = "REPLACE_WITH_YOUR_DOKPLOY_API_KEY"
```

把引号里的占位符换成真实密钥，**双引号留着**，保存。只改这一处，别整份覆盖。

然后回设置 → 插件 → MCP，找到 dokploy，确认开关是开的。配置刚改过的话，点齿轮重新加载一下。列表没更新就退出重开一次，第一次启动要下依赖，会慢一点。

### 3.验证连通性

这一步很多人跳过，我觉得不该跳。用最简单的只读指令确认链路通不通：

```
请通过 Dokploy MCP 列出当前项目。
只读取信息，不创建或修改任何资源。
如果连接失败，报告具体错误。
```



**返回空列表是正常的**——你刚装完当然没项目。

判断成功的关键不是它返回了什么内容，而是**它真的调用了工具、拿到了 Dokploy 的返回**。如果它只是在给你讲解"你可以这样操作"，那就是没连上，别被忽悠过去。

通了之后再加一条：

```
请通过 Dokploy MCP 创建 personal-stack 项目。
完成后告诉我项目名称和 ID。
```

![img](https://imgoss.xgss.net/picgo-tx2026/QQ_1793149703323.png?tx)

回面板 Projects 页面刷新一下，项目出现了，链路就成立了。

### 4.让它部署一套 Supabase

光建空项目没意思，来点真的。

Supabase 是什么？一句话：**给你的网站提供数据库、登录和文件存储的后台**。做个备忘录、做个记账本，用户账号和数据都存在它那儿。

一条指令丢过去，重点是把要求写细：

```
请通过 Dokploy MCP，在 personal-stack 项目中部署 Supabase。

要求：
1. 使用已经检查过的 Supabase 模板，避免重复创建已有服务。
2. 检查模板版本、所需配置和数据持久化挂载。
3. 确认密码及密钥已安全生成，不使用默认示例凭据，
   不在回复中显示真实密钥。
4. 根据我提供的访问地址配置 API 地址与认证回调；
   如果地址或必要配置缺失，先告诉我，不要猜。
5. 不向公网开放数据库端口，不修改其他服务。
6. 执行部署后检查部署记录和关键服务状态，
   告诉我如何打开管理入口、如何验证 API。
7. 工具无法检查的部分明确说明，不以"已提交部署"代替成功。
```



第 5 条和第 7 条是我认为最该加的：**别把数据库端口暴露到公网**，以及**"提交了部署"不等于"部署成功了"**——这两句能省掉你后面一堆心累。

怎么算是真部署好了？三个检查：

- 部署记录里没有失败、没有一直在重试
- 数据库、认证、API 网关这些关键服务状态是正常的
- 管理入口能登进去，API 能真的请求通



### 5.做一个连接它的网站

Supabase 通了，继续让它做个带登录的备忘录：

```
请帮我制作一个连接这套自托管 Supabase 的个人备忘录网站。
实现登录、查看、新增、编辑和删除自己的笔记。

提供建表 SQL 和 RLS 策略，确保用户只能操作自己的记录。
浏览器端只使用公开客户端密钥，不使用 service_role 或 secret key。
先在本地检查代码和配置，再通过 Dokploy MCP 部署网站。
数据库初始化如果需要其他工具，请明确告诉我如何完成。

最后验证：保存后重新登录数据仍在，两个测试用户不能访问对方的笔记。
```



注意最后那句验证要求——**保存后重新登录数据还在**，以及**两个测试账号互看不到对方的笔记**。这两条才是"真的接上了"的标准。能打开首页不算。

### 6.接上 GitHub，推代码就自动上线

前面已经搞定"网站能跑、数据能存"。接下来把代码放进 GitHub，让服务器自己拉、自己构建。

**第一步是授权。** 打开 Dokploy 左侧 **Git** → **GitHub**，URL 保持 `https://github.com`（这里填平台地址，不是仓库地址），点 **Create GitHub App**，跟着跳转页面走完。

回到 Dokploy，列表里会多出一个 GitHub App，但右边显示 **Action Required**——**这说明还没完成仓库授权**，很多人以为到这步就完了。

点 Action Required 右边、垃圾桶左边那个安装图标，进 GitHub 的安装页。这里有个细节：**选"仅选定的仓库"**，只授权你要部署的那一个，别图省事选全部仓库。授权范围越窄越安全。

完成后跳回 Dokploy，Action Required 变成正常状态，就成了。

**第二步交给 AI。** 回对话里发：

```
请通过 Dokploy 官方 MCP 部署 GitHub 仓库：
你的用户名/你的仓库名，分支 main。

使用刚刚连接的 GitHub Provider，
在 personal-stack 项目中创建独立服务。

先读取仓库，根据实际代码配置构建和运行方式。
复用现有 PostgreSQL 和 PostgREST，不重复创建数据库，
保留已有数据和数据卷，凭证从本地配置读取，不输出。

先确认新服务正常，再切换网站路由，保留回退方式。
开启 main 分支推送后的自动部署。
完成后返回访问地址、部署结果和本次对应的提交。
```

**第三步验一下自动部署是不是真的生效。** 让 AI 改点界面再推送：

```
请修改这个项目的界面：
改成浅色背景、绿色按钮和卡片式列表，标题改为"我的个人备忘录"。
保留新增、编辑、删除功能。

完成后提交并推送到 GitHub 的 main 分支。
推送后不要手动触发 Dokploy 部署。
观察自动部署记录，确认网页更新，原有数据仍然存在。
```

推完你不用点任何按钮，Dokploy 那边会自己出现一条对应这次提交的部署记录。刷新网页，新界面就上来了——**而且之前存的记录还在**。

到这里，整条链路就闭环了：

> **AI 改代码 → 推 GitHub → Dokploy 自动构建 → 刷新就能看到新版**

跟 Vercel 的体验不能说相似，基本就是一样。区别是——这台机器是你的。



## 日常运维：也可以直接问 AI

部署只是第一次。真正高频的是"它挂了没""报什么错""要不要重启"。

下面几条指令可以直接抄：

**看状态**

```
通过 Dokploy MCP 检查 my-web 的状态和最近一次部署结果。
先只读取，不重启、不重新部署。
区分已经确认的问题和需要继续检查的地方。
```

**查失败原因**

```
检查 my-web 最近一次失败的部署。
读取当前工具能获取的日志，指出关键报错并解释可能原因。
先给出建议，不要连续重试部署。
如果 MCP 无法读取日志，告诉我去面板哪里查看。
```

**改环境变量**

```
将 my-web 的 LOG_LEVEL 设置为 info，保留其他环境变量。
先判断修改是在构建时还是运行时生效，
然后执行必要的重新部署并检查结果。
不要输出其他变量中的密钥。
```

**看资源占用**

```
检查服务器和应用的资源使用情况，只读取信息。
不停止服务、不清理文件。
说明内存统计口径，区分总量、已用量和可用量。
```

用 AI 做运维，我踩过的教训就一条：**指令要写清"操作哪个、改什么、保留什么、最后怎么验证"。** 最好分两步走——先让它诊断、给建议，你看着没错再让它动手。一步到位的指令省事，但出问题时你都不知道它改了哪儿。

## 写在最后

以前聊"自建服务""买 VPS"，感觉那是运维和全栈工程师的领域，普通人碰不了。

现在这套组合把门槛削掉了一大半。你不用背 Linux 命令，不用在云厂商后台迷路——**海外节点云服务器，剩下的丢给 AI 对话搞定。**

换来的是：跟 Vercel 一样丝滑的自动部署，没有任何平台的额度和网络限制，数据和基础设施全在自己手里。

有朋友问我值不值。我的答案是：**如果你只是把静态页面放上去给人看，Vercel 挺好，别折腾。但如果你要长期养一个带数据库、要跑后台任务的东西，那这一百块花得太值了。**
